# 宠宠欲动 Petitch · 系统架构与联调约定

**队伍「怪人协会」｜3 人｜LifeHack｜2026 年 11 月 18–30 日（北京时间）**

评委在手机上从首页做六题，看到三种推荐及理由，再针对第一名体验五个真实照护场景。先验收这条路径，再看页面是否好看。本文供三人在 Qoder 里实施；GitHub 的 Petitch 公共仓库保存版本，Qoder Sites 提供作品公开链接。

## 1. 从首页到领养准备

| 路由 | 打开方式和页面内容 | 组件与负责人 |
|---|---|---|
| `#/` | 一句话「先找到适合你的宠物类型，再决定要不要领养」、开始匹配、固定三张热门卡；点卡看详情，也能进入领养指南 | A · HomePage、PetCard、AppShell |
| `#/quiz` | 六题依次为住房、陪伴时间、经验、过敏、月预算、安静或活泼；一题一屏，显示第几题和总数，单选后推进，可退回改选；末题确认后看结果 | A · QuizPage、ChoiceGroup、ProgressBar |
| `#/results` | 三张卡显示名称、整数匹配度和一句理由；三种都可查看详情，仅第一名有试养按钮；可重新测 | A · ResultsPage、MatchCard |
| `#/pets/:id` | 顶部放难度、月花费区间、寿命；下方展示性格、空间和陪伴需求、掉毛、叫声、粘人、运动量、过敏友好度、适合人群、注意事项；可收藏、进入该类型清单 | A · PetDetailPage，C · FavoriteButton |
| `#/trial` | 从结果第一名进入。五张卡逐张选，顶部显示忍受度；结束后原页展示分数、结论和扣分点，给出下一步 | C · TrialPage、ScenarioCard、TrialSummary |
| `#/guide` | 意向申请 → 初筛沟通 → 线下见面 → 正式领养；列渠道类型及防骗提醒 | A · GuidePage，B · 文案 |
| `#/checklist/:id` | 标题显示当前宠物，5–7 个带文字的勾选项，随勾随存 | A · ChecklistPage，C · 勾选控件与存储 |

八项功能占七个页面：收藏嵌在详情里。所有页面保留回首页入口。首页固定选三种即可，「热门」无需计数。附件的额外设想不进入本届排期。

## 2. 技术边界和文件归属

Vite + React（JavaScript）+ Tailwind + HashRouter。使用组件状态、纯函数和浏览器存储。八项功能都可在浏览器运行，必须自建的后端为零。构建产物含静态前端及内置数据。两次问卷之间可以共享收藏，两个访客的收藏各自独立。

| 建议位置 | 内容 | 修改人 |
|---|---|---|
| src/App.jsx、src/pages/、src/components/、src/styles/ | 路由、首页、问卷、结果、详情、指南、清单、公共视觉组件 | A |
| src/data/pets.json、scores.json、scenarios.json、checklists.json | 分别存原表中四组资料，沿用原字段、取值、顺序、分组和文本单位；JSON 文件均在 src/data 下 | B |
| src/data/questions.js、catalog.js、guide.js | 六题配置、原表读取与标识映射、指南文案。页面通过 catalog 读取原表 | B |
| src/logic/match.js、tests/match.test.js | 排名、推荐理由及规则测试 | B |
| src/features/trial/、src/features/saved/、对应测试 | 试养页面及判定、收藏、清单勾选与浏览器存储 | C |
| src/logic/quizSession.js | 当前标签页的答案读写，结果页和试养页共享同一份 | A |
| 根目录构建配置、依赖锁文件、发布版本 | 一人维护安装和构建配置，其他人复用已提交的锁文件 | A |

宠物顺序固定为狗、猫、兔子、仓鼠、鹦鹉、乌龟、龙猫、刺猬、金鱼、守宫、荷兰猪、雪貂；同分时以原表顺序为准。附件称原始资料已写入 pet-data-table.md，本次未取得该文件。B 开工先从队内拿原表。若尚未拿到，用明确标识的测试样例联调，记录待核项，正式数据验收前必须逐项回到原表。不要让 Qoder 猜月花费、寿命、条目或量表方向。

## 3. 三人第一次联调就要签下的接口

以下是运行时接口，原始资料无须新增字段。若原表只有中文名，B 在 catalog 中用固定映射生成路由标识。清单项沿用已有标识，缺少时在映射层固定赋值，避免按页面当前位置保存。

| 接口 | 输入 | 返回与调用方 |
|---|---|---|
| questions | 无 | 有序的六个题目对象，每个含 id、title、options；选项含 id、label。A 渲染，B 维护映射 |
| getPet(id)、listPets() | 固定宠物标识或无参数 | 指定资料或原表顺序的全部资料。未知 id 返回 null，A 展示返回首页入口 |
| rankPets(answers) | 键为题目 id、值为选项 id 的对象 | 完整有效时返回三项，每项含 petId、percent、reason；不全或含无效选项时返回空数组。A 和 C 调同一函数 |
| readAnswers()、saveAnswers(answers)、clearAnswers() | 当前六题选项 | A 写 sessionStorage，C 从同模块读；重新测清除旧轮次 |
| getScenarios(petId)、getChecklist(petId) | 目录中有效的宠物 id | 分别返回五个场景、5–7 项清单。场景视图含 id、text，清单视图含 id、label |
| FavoriteButton、ChecklistItems | 前者收 petId，后者收 petId 与 items | C 自行读写状态，A 挂载组件；切换宠物后立即呈现对应状态 |
| TrialPage | 通过 readAnswers 和 rankPets 派生 Top 1 | 缺有效答案回问卷；按 Top 1 取卡，拒绝用任意 URL 参数指定其他类型 |

目录展示字段的具体键名由 B 在 18 日给 A 一份真实样例及对照。页面读取数据、纯函数计算、组件渲染三步分开。A 给 C 留好导出接口，C 的 PR 合并后 A 再接入路由，避免主分支引用尚不存在的模块。

## 4. 六题怎样变成三个有理由的推荐

以下权重与量表映射是团队起始设计。18 日 B 需在原表标明高分含义后才落代码。若原表已经给出某选项对宠物的 **契合分**，直接取原分，不再计算距离。若给的是 **属性档位**，在读取层依下表换算为 1–5 契合分。原表值一直保留。

| 题／权重 | 原表对应项 | 算法 |
|---|---|---|
| 住房 2 | 空间需求 | 先把可提供量和需求统一为 1–5 档。契合分 = 5 − max(0, 需求 − 可提供) |
| 陪伴 3 | 陪伴需求 | 同上，时间富余不扣分 |
| 经验 1 | 饲养难度 | 将经验映射为可应对难度，同上 |
| 过敏 3 | 过敏友好度 | 有顾虑按友好度正向计分；无顾虑跳过，不计入分母。避免作个人过敏风险保证 |
| 预算 2 | 预算需求 | 用原表预算数值档位与问卷预算档位计算满足度；月花费文案仅负责展示 |
| 安静或活泼 1 | 安静/活跃对应项 | 同向档位后取 5 − abs(用户偏好 − 属性档)。若原表需结合叫声和运动量，两者分别算契合分取平均，整题仍占权重 1 |

为每只宠物计算 S = Σ(契合分 × 题目权重)，W = 有效题目的权重和。用 S / (5W) 从高到低排序；完全同分按原表顺序。取前三，再将比值乘 100 四舍五入。百分比解释为生活条件的规则契合度。理由从有效题中选契合分最高项，并列先取高权重、再次并列按题序。例：「你每天能投入的陪伴时间有限，它所需的陪伴时间也较短。」若最高项也只有 3 分或更低，改为指出最大短板，避免误导。

**手算示范（虚构分值，仅验公式）。** 按表中题序，某宠物六项契合分为 5、4、5、跳过、3、4。加权和 = 10 + 12 + 5 + 6 + 4 = 37，有效权重 = 9，显示 82%。若「有过敏顾虑」且该维为 2 分，新结果为 43 / 60，显示 72%。测试另覆盖同分、取整后相同但原始分不同、不全答案及回退改选。

## 5. 试养和存储的边界

- 从本轮第一名取五张卡。狗、猫、兔子、仓鼠、鹦鹉各用自己的五张，余下七种统一读五张通用卡。库存总数为 5 × 5 + 5 = 30。通用卡文案应适用于含金鱼、守宫在内的七种对象。
- 三个选项依次扣 0、5、20 分。保留按卡标识记录的五次选择，忍受度 = 100 − 扣分合计。只有本卡首次确认可推进。刷新试养页从本轮 Top 1 的第一张重新开始；刷新结果页仍可重算排名。
- 原需求在 85 分重叠。统一为分数 <60 劝退，60–85 含两端提醒，>85 适合。劝退展示延后决定、云养宠或到收容所做志愿者；提醒显示扣分点；适合进入对应清单。三档均可进入指南。
- 四个可复现例子（括号内为五张卡分别扣分）：55（20,20,5,0,0），60（20,20,0,0,0），85（5,5,5,0,0），90（5,5,0,0,0）。
- localStorage 的 petitch.favorites.v1 保存类型标识数组；petitch.checklists.v1 保存“宠物标识 → 已勾选条目标识数组”。每次更新按当前宠物合并，保留其他类型。缺键或坏 JSON 回到空状态。sessionStorage 的 petitch.answers.v1 记录当前答案；读出后验证题目和选项。无效链接给明确返回入口。

## 7. 在 Qoder 中使用本文件

三人先在各自 Qoder 打开同一个 GitHub 仓库的本地副本，把本架构和自己的手册附到对应任务，粘贴手册中当天提示词。GitHub 用于同步版本，开发、修复、测试命令和站点打包在 Qoder 完成。首次联调优先合 A 的脚手架、B 的数据接口，再合引用方。每个 PR 写清测试输入、实际结果、接收人。

**架构核对提示词（可直接粘贴）**

> 请读取当前 Petitch 仓库、本架构文件和我的岗位手册。先查看现有目录、锁文件、当前分支和原表是否可读，给出“已有文件、今日需改文件、所依赖的队友交付、今天的可验证结果”。按手册只执行今天我负责的任务，沿用已合并接口。原表缺失时列出缺项并继续独立工作。把实际执行过的命令与仍需本人在手机或天池上操作的步骤分开报告。供我审阅 diff 后自行提交。
